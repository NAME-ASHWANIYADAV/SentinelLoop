# Threat model

**Scope:** a single-site deployment of SentinelLoop (`SYSTEM_ARCHITECTURE.md`): the REST API, the operator console, the admin CLI and the CMMS connector.
**Method:** assets, trust boundaries and entry points, then STRIDE per entry point, with the mitigation and its status.
**Status of evidence:** automated tests, an automated code security review, and the Phase 9 adversarial review (role-played reviewers, including an IT/OT security assessor: `ADVERSARIAL_REVIEW.md`). Findings were fixed test-first (PD-14). **No penetration test or external security review has been done.** This model is not a compliance claim. Updated 2026-10-18 to match the code after the Phase 9 fixes.

## 1. What must be protected

| asset | why it matters |
|---|---|
| Integrity of recommendations and states | a manipulated reading, model, rule or state could hide an urgent condition or create needless work orders |
| Work requests in the customer's CMMS | in `draft_requests` mode, field crews may act on what SentinelLoop writes there |
| Audit trail | the evidence of who decided what; needed for any post-incident review |
| Model artefacts | a replaced pickle executes code on load, inside the API process that holds the audit key and the CMMS credentials |
| Credentials: API keys, the audit key, CMMS API keys and webhook secrets (`SENTINELLOOP_CRED_*`) | they give access, the ability to forge audit events, or write access to the CMMS |
| Customer operational data: SCADA, work orders, technician names | commercially sensitive; personal data in technician fields (India's DPDP Act, per R5, not re-verified) |
| Availability of the service | lost assessments mean lost warnings; the plant itself must not depend on SentinelLoop (§4) |

## 2. Trust boundaries and entry points

1. **REST API** (`/api/v1`). Clients: integration jobs, the operator console, scripts.
2. **File and CSV ingestion** through the API: content from SCADA exports.
3. **Model bundle directory** on disk.
4. **Database file** and its backups on disk.
5. **Administration CLI** on the host. It reads its secrets from the environment.
6. **CMMS connection** (outbound only): Odoo JSON-2 calls or a signed webhook POST, from the API process. The platform exposes **no inbound webhook endpoint**; `integration.verify_webhook` is the reference check for receivers.
7. **Downloaded public datasets** (G0): untrusted archives.
8. **Operator console** (Streamlit, `src/sentinelloop/console/`). It binds to 127.0.0.1:8501 (`.streamlit/config.toml`), calls the API with the signed-in user's own key, and gets the API URL from server configuration (`SENTINELLOOP_API_URL`), never from the user.

## 3. STRIDE

| # | threat | entry | mitigation | status |
|---|---|---|---|---|
| S1 | Spoofing a user or integration | API | 256-bit API keys, stored as SHA-256 and compared in constant time; scrypt passwords (min 12 chars); deactivation revokes keys; every route except `/health`, `/ready`, `/docs` and `/openapi.json` needs a key (a test walks all routes). `/ready` and the OpenAPI schema are unauthenticated **by decision** (security-10): they reveal schema version, approved-model count, audit-key and decision-config status and the API surface, not data or secrets | IMPLEMENTED_AND_TESTED. No SSO and no key expiry (residual) |
| S2 | Credential theft from the database | DB file | no plaintext keys or passwords stored; the user listing never returns hashes; CMMS credentials are never stored (only the name of an environment variable) | IMPLEMENTED_AND_TESTED |
| S3 | A stolen console session or key | console | the console binds to localhost; TLS and remote access through a reverse proxy or VPN (`DEPLOYMENT_GUIDE.md` §5); each user signs in with a personal key, so the API's role checks apply | IMPLEMENTED_AND_TESTED (binding by configuration: `test_the_console_binds_to_localhost_by_configuration`). Keys are long-lived and the console has no idle timeout, only a sign-out button (residual) |
| T1 | Tampering with readings to hide a fault | ingestion | unit and range contract; conflicts rejected rather than overwritten; batches hashed and audited; implausible values flagged | IMPLEMENTED_AND_TESTED. A compromised source system, or a stolen `integration` key, sending plausible false data is **not** detectable by the platform (residual) |
| T2 | Tampering with the audit trail | DB file | HMAC chain over audit events with a key outside the database; fail-closed key (PD-07); each backup writes an anchor (seq, hash); `admin verify-audit` refuses to run without an anchor unless `--allow-no-anchor` is given (PD-22). The chain plus an anchor detects edits, reordering and removal of events, and truncation, **only when verified against an anchor kept off the host**, and only for events up to that anchor. Verifying a backup against the anchor written beside it shows only that the copy is self-consistent. **The anchor requirement is in the CLI only:** `GET /api/v1/audit/verify` takes an optional anchor (`anchor_seq`, `anchor_hash`) and without one checks internal consistency only; the console's "Verify the audit chain" button sends none and shows a green "valid: True" that cannot detect truncation (`console/app.py`, `page_audit`; `console/client.py`, `verify_audit`; `api.py`, `audit_verify`) | IMPLEMENTED_AND_TESTED for the CLI (`test_audit_anchor_detects_truncation`, `test_verify_audit_requires_an_anchor_unless_explicitly_waived`, recovery drill `product/evidence/recovery/r1.md`). The API route and the console button verify without an anchor (residual; `test_roles_are_enforced_with_403` asserts `valid` for an anchorless API verify). Residual: anchors are unsigned, so their protection is where they are kept; an attacker holding the database and the audit key can rewrite events newer than the last off-host anchor |
| T3 | Replacing a model bundle (code execution through pickle) | bundle dir | registration hashes `bundle.pkl` and refuses a mismatch with its manifest (security-13); the registry stores that hash; loading refuses a mismatch before unpickling; bundles come only from our packaging code | IMPLEMENTED_AND_TESTED (`test_registration_refuses_an_artefact_that_does_not_match_its_manifest`, F10 in `RELIABILITY_AND_SAFETY.md`). A bundle altered together with its manifest before registration is accepted, and an attacker who can write both the bundle and the registry row can execute code, which also exposes the audit key and the CMMS credentials in the process environment (residual: file permissions; PLANNED: signed manifests) |
| T4 | Changing policy thresholds silently | config files | the policy SHA-256 is stored with each assessment; the site decision config is validated (unknown keys and negative values refused) and `/ready` says whether one is loaded (PD-24) | IMPLEMENTED. Change control for the files is operational (runbook) |
| T5 | Editing state tables directly (users, asset states, work orders, readings) | DB file | none in the platform: the audit chain covers audit events, not state tables (PD-22). Host access and file permissions are the control | NOT_SUPPORTED (residual; KNOWN_LIMITATIONS S7) |
| T6 | Silencing recommendations or clearing a data failure with chosen assessment instants | API (`assess`) | an `as_of` more than 5 min in the future is refused; an instant at or before the last applied one is stored as a replay that never moves the live state (security-2) | IMPLEMENTED_AND_TESTED (`test_future_assessment_instants_are_refused`, `test_back_dated_assessments_are_stored_but_never_move_the_live_state`) |
| T7 | Clearing a latched warning without an inspection | API (work orders, `clear-risk`) | PD-16: only a person's completion of a later order that addresses the equipment and records an inspection, or a reasoned dismissal by a planner, reliability engineer or admin; machine-role completions never clear (security-1, security-5). The rule that `clear-risk` records dismissals only is enforced in the API route alone (`api.py`, `clear_risk`): `health.clear_latched_risk` and `states.clear_risk` still accept `maintenance_completed`, with free text and no work order, from technicians, planners, reliability engineers and admins (`states.CLEAR_EVENTS`) | IMPLEMENTED_AND_TESTED at the API and in `workorders.complete` (`tests/test_app_remediation.py`). Residual: a direct service call, a new route or a script bypasses PD-16 (E1); `tests/test_app_states.py::test_maintenance_completion_clears_the_latched_risk` still clears a latch that way. A technician key can clear a latch with a false inspection outcome (§4) |
| T8 | Injecting links, images or fake "approved by" text into console pages through free text | console | all API-sourced text is rendered inside code spans, where no markdown, link, image or autolink can form (security-12) | IMPLEMENTED_AND_TESTED (`test_console_renders_api_text_as_code_spans_with_no_links`) |

## 4. Safety boundary

SentinelLoop is **advisory**. It has no connection to control systems and cannot start, stop or reconfigure equipment.

**The worst outcome of a compromise**, stated as it is:
- **Inside SentinelLoop:** warnings hidden or delayed and needless work orders. A stolen planner, reliability-engineer or admin key can dismiss latched warnings with a typed reason. A stolen `integration` key can feed plausible false readings (T1) and generate recommendations. It can also create work orders and submit them for approval, complete any IN_PROGRESS order with an invented outcome (which never clears a latch), and run CMMS dispatch (`security.PERMISSIONS`, `workorders.TRANSITIONS`, `integration.DISPATCHERS`). It cannot approve work. A stolen technician key can clear a latch by starting and completing, with a false `no_fault_found` outcome, any scheduled order that was raised after the latch began and is not an `instrument_check` or `desk_review`; there are no assignment checks (security-5). A database writer can edit state tables undetected (T5).
- **In the customer's CMMS** (only in `draft_requests` mode): false, altered or stale maintenance requests marked `[SentinelLoop]`, at up to Odoo priority '3', the top of its scale, which crews may act on. An approver key is enough to approve work that is then sent; an admin key can also switch a target out of shadow mode. After dispatch, an invented completion by a stolen `integration` key is mirrored onto the crew's real request as `[SentinelLoop COMPLETED]` with the text "Do not act on it unless your own process says so" (`integration.odoo_payload`), which can lead a crew to drop real work. Code execution in the API process (for example through T3) exposes the CMMS API key, with whatever rights the CMMS user has, and the audit key.
- **Physical harm** can follow indirectly: people act on a false request (for example an unneeded climb in bad weather), or a real warning is suppressed and nobody else catches it. The platform itself cannot actuate anything.

**Plant safety must never depend on SentinelLoop.** It is not part of any safety function, claims no SIL and takes no credit as a protection layer (`RELIABILITY_AND_SAFETY.md` §1). A turbine's own protection systems and the operator's procedures stay in charge. This is written in `RELIABILITY_AND_SAFETY.md` and on the console's sign-in page. No customer has been contacted, so it has not yet been stated to one; it belongs in any pilot agreement (`PILOT_PROTOCOL.md`).

## 5. Deployment assumptions

These are written into `DEPLOYMENT_GUIDE.md`.
- TLS is terminated by a reverse proxy in front of the API and the console; both bind to localhost (the console through `.streamlit/config.toml`).
- The audit key and the database live on different storage, or the key is in a secret store.
- Host access is restricted to administrators; the bundle directory and database file are not world-writable.
- Backups are encrypted at rest by the hosting environment. Their anchors are copied off the host, and the daily verification uses an earlier anchor from there.
- CMMS credentials are in `SENTINELLOOP_CRED_*` environment variables for a dedicated least-privilege CMMS user, and `SENTINELLOOP_INTEGRATION_HOSTS` lists only the CMMS host.

## 6. Open items

- External penetration test before any customer deployment that is reachable beyond one host.
- Signed model manifests (an asymmetric signature), so that a database writer cannot also register a malicious bundle.
- Role checks inside the services that rely on the API check alone (E1), starting with user administration; `decision.generate` to take the caller's role.
- `maintenance_completed` removed from the clearing events that `health.clear_latched_risk` accepts, so PD-16 holds below the API route (T7).
- An anchor required, or the result labelled "no anchor: truncation not checked", on `GET /audit/verify` and the console's verify button (T2).
- Splitting the `integration` role into ingest, dispatch and CMMS-sync roles; assignment checks on work orders (security-5).
- Integrity of state tables (T5) if a customer needs it; automated, monotonic anchor history off the host (T2).
- Running the connector against a real Odoo sandbox (pending image-download approval).
- Dependency upgrades and a hash-locked, platform-only requirement set audited with OSV (`SECURITY_REVIEW.md` §3).
- SSO or OIDC for customer identity providers; key expiry.
