# Product Claim–Evidence Matrix

Every capability the product may claim, with its status, the evidence behind it and how to reproduce it. Status vocabulary (PD-03, with the same definitions as `FINAL_PRODUCT_HANDOFF.md` §2): **IMPLEMENTED_AND_TESTED** (the code exists and automated tests or recorded runs exercise it; it says nothing about real equipment), **IMPLEMENTED_NOT_FIELD_VALIDATED** (it works on our data, and its value depends on real data or real users it has never met), **SIMULATED** (only demonstrated on simulated or synthetic data), **PLANNED**, **BLOCKED** (needs something we do not have), **NOT_SUPPORTED** (our own evidence contradicts it). No capability in this matrix has been field-validated.

Data provenance labels used below: C-MAPSS = NASA simulated turbofan engines (public, simulated); INJECTED = faults we injected into C-MAPSS; SYNTHETIC = generated by our own code (the wind generator `app/synthetic_wind.py`, or test fixtures); PUBLIC REAL = public field data (CARE to Compare: not downloaded, not used). No customer data has been used anywhere.

How to read the rows:
- Rows P1–P16 were first set by the Phase 0 audit of the competition baseline (tag `competition-baseline`). Every row was re-checked against the code, the tests and the evidence files on 2026-10-18: after the Phase 9 review fixes, the re-review fixes and W3 (commits 38e8741 to 2f281fe), and again after the fixes from the final handoff audit (`tests/test_app_handoff_fixes.py`). Rows P21–P31 cover capabilities added in Phases 5–9.
- **Competition pipeline only** marks a capability that exists only in the frozen competition code (`src/sentinelloop/*.py` outside `app/` and `console/`). The product platform (`src/sentinelloop/app/`, `src/sentinelloop/console/`) does not have it (review finding buyer-3).
- Each evidence cell carries the unfavourable part of the same evidence after **Against:** (buyer-7). A NOT_SUPPORTED or BLOCKED row is itself the unfavourable result.
- Detection and lead-time figures from our synthetic wind generator are behaviour checks: the generator sets them. They are never evidence of performance (data_scientist-10, `KNOWN_LIMITATIONS.md` E3).
- Test counts are per file, from `pytest --collect-only` on 2026-10-18 (a parametrised test counts once per case).
- Some reproduce commands need git-ignored local data, and the tests that use it skip without it: the NASA C-MAPSS files (`python -m sentinelloop data --download`) for `tests/test_app_health.py` and the competition tests on real data, and the out-of-fold table written by `python experiments/run_all.py` for `tests/test_app_sim.py`. In a clean clone 27 tests skip for this reason: the full suite gives 582 passed, 28 skipped, and the platform tests (`python -m pytest tests -k "test_app_ or test_console"`, the same tests as `tests/test_app_*.py tests/test_console.py` in a POSIX shell) 474 passed, 22 skipped (checked on a copy of the working tree without the local data, including `tests/test_app_handoff_fixes.py`); the remaining skip in each is the Odoo sandbox test.
- References: a bare P-number (P19, P29) is a row of this matrix; "KL" plus an ID (KL E3, KL P10) is a row of `KNOWN_LIMITATIONS.md`; "TECHNICAL_DEBT" plus an ID (TECHNICAL_DEBT B2, TECHNICAL_DEBT F1) is a row of `TECHNICAL_DEBT.md`; F-rows are its §F.
